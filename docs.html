Secureye developer reference

Integration takes under 10 minutes

Secureye is a drop-in replacement for CAPTCHA. It verifies human presence using eye liveness (camera) or keystroke rhythm (keyboard) — all processed client-side. No biometric data ever leaves the user's device.

Quickstart

Three steps: get a sitekey, embed the widget, validate the token server-side.

  • 1

    Get a sitekey

    Register at secureye.io → Free tier gives you 10,000 verifications per month. No credit card needed. You'll receive two keys: a public sitekey for the frontend and a private secret key for your backend.

  • 2

    Embed the widget

    Add the script to your <head> and place the widget div wherever you need verification — login forms, signup, checkout, comment boxes.

    HTML 
    <!-- Load Secureye once, in <head> -->
<script src="https://cdn.secureye.io/secureye.js" defer></script>

<!-- Place the widget in your form -->
<div
  class="secureye-widget"
  data-sitekey="YOUR_SITEKEY"
  data-callback="onVerified"
></div>

<script>
  function onVerified(token) {
    // send token to your backend with the form
    document.getElementById('token-field').value = token;
    document.getElementById('my-form').submit();
  }
</script>
  • 3

    Validate server-side

    When your backend receives the form, POST the token to our API before processing. Never trust the token without server-side validation — client-side verification alone is not enough.

    Node.js 
    const res = await fetch('https://api.secureye.io/v1/verify', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    secret: process.env.SECUREYE_SECRET,
    token:  req.body.secureye_token,
  }),
});

const { success } = await res.json();
if (!success) return res.status(400).json({ error: 'Verification failed' });
    ✓

    Tokens are single-use and expire in 60 seconds. Your validation endpoint should be called immediately after form submission — don't cache or reuse tokens.

How it works

Understanding the verification flow helps you integrate securely and handle edge cases correctly.

Verification flow

When a user encounters the Secureye widget:

  1. Mode detection — The widget checks for camera availability via navigator.mediaDevices.enumerateDevices(). Camera present → eye mode. Keyboard only → keystroke mode. The user can always switch manually.
  2. On-device processing — A lightweight WebAssembly model analyzes the camera feed or keystroke timings locally. The raw data never leaves the browser.
  3. Token issuance — On success, Secureye servers issue a signed JWT bound to your sitekey and the current timestamp.
  4. Server validation — Your backend sends the token to /v1/verify. We verify the signature, check it hasn't been used, and confirm it's within 60 seconds of issuance.
  5. Forget — The token is marked as used. No user data is retained. The session is complete.
ℹ

The Secureye widget loads inside an iframe with allow="camera". Camera permission is requested from the iframe origin (secureye.io), not your domain — so users see a single consistent permission prompt across all sites using Secureye.

HTML widget

The widget is a <div> that the Secureye script enhances into a full verification UI. It mounts an iframe that handles camera permissions, verification logic, and the visual interface.

HTML 
<div
  class="secureye-widget"
  data-sitekey="YOUR_SITEKEY"
  data-callback="onVerified"
  data-error-callback="onError"
  data-theme="dark"
  data-mode="auto"
></div>

Widget attributes

data-sitekey required
string
Your public sitekey from the Secureye dashboard. This is safe to include in client-side code — it identifies your site but cannot be used to validate tokens.
data-callback optional
string (function name)
Name of a global function to call when verification succeeds. Receives the token string as its only argument. If omitted, listen for the secureye:verified event instead.
data-error-callback optional
string (function name)
Called when verification fails or the user denies camera permission. Receives an error object { code, message }.
data-theme optional
"dark" | "light"
Widget color scheme. Defaults to "dark". Use "light" for sites with light backgrounds.
data-mode optional
"auto" | "eye" | "key"
Force a specific verification mode. "auto" (default) detects camera availability and picks the best mode. Force "key" if you want keystroke-only (e.g. for accessibility).

JavaScript API

For programmatic control — useful for single-page apps, custom form flows, or when you need to trigger verification without a visible widget.

JavaScript 
// Trigger verification manually
Secureye.execute('YOUR_SITEKEY', {
  callback: onVerified,
  errorCallback: onError,
  theme: 'dark',
  mode: 'auto',
});

// Reset the widget (e.g. after a failed form submission)
Secureye.reset();

// Listen via DOM events instead of callbacks
document.querySelector('.secureye-widget')
  .addEventListener('secureye:verified', (e) => {
    console.log(e.detail.token);
  });

document.querySelector('.secureye-widget')
  .addEventListener('secureye:error', (e) => {
    console.error(e.detail.code, e.detail.message);
  });

Server validation

Always validate tokens on your backend before processing a request. A token on its own is not proof — you need to confirm it was issued by Secureye servers and hasn't been used.

Endpoint

HTTP
POST https://api.secureye.io/v1/verify
Content-Type: application/json

Request body

secret required
string
Your secret key from the dashboard. Never expose this in client-side code.
token required
string
The token received from the client widget callback.

Success response

200 OK
JSON
{
  "success":    true,
  "mode":       "eye",         // "eye" or "key"
  "issued_at":  "2025-11-01T14:23:01Z",
  "hostname":   "yoursite.com"
}

Failure response

200 OK
JSON
{
  "success":      false,
  "error-codes": ["token-expired"]
}
⚠

The API always returns 200 OK — check the success field, not the HTTP status code. Network errors or 5xx responses should be treated as verification failure.

Verification modes

Eye mode (camera)

The default on any device with a front-facing camera. A lightweight liveness detection model runs in WebAssembly inside the browser. It checks for:

  • Live face presence (not a photo or screen replay)
  • Natural eye movement and blinking
  • Depth cues that defeat flat image spoofing

The camera feed is processed frame-by-frame in memory and immediately discarded. No frames are stored, buffered, or transmitted.

Keystroke mode (keyboard)

The fallback for devices without a camera, or for users who prefer not to use their camera. The user types a randomly selected short phrase. The widget measures:

  • Dwell time — how long each key is held
  • Flight time — the gap between releasing one key and pressing the next
  • Rhythm variance — humans type in organic bursts; bots are too consistent
✓

To force keystroke mode for all users (e.g. for accessibility or privacy-conscious audiences), set data-mode="key" on the widget.

Privacy architecture

Secureye is designed so that storing biometric data is architecturally impossible, not just a policy choice.

Data typeWhat happens to it
Camera feedProcessed frame-by-frame in WebAssembly. Never buffered, never transmitted.
Keystroke timingsComputed in JS memory, used to generate a pass/fail signal, then discarded.
Verification tokenA signed JWT with no user data. Contains: sitekey, timestamp, mode. Expires in 60s.
IP addressLogged for rate-limiting only, purged after 24 hours.
User identityWe have no concept of a user. Each verification is stateless and independent.

The client-side verification code is open source. You can audit exactly what runs in your users' browsers before deploying.

Self-hosting

The widget and verification UI are plain static files. You can serve secureye.js and verify.html from your own domain.

bash
git clone https://github.com/secureye/secureye
cd secureye
# serve with any static file server
npx serve .

Token signing requires a backend with your private key. When self-hosting, you run your own signing service and point secureye.js at it. See the self-hosting guide for the full setup.

⚠

Self-hosted deployments bypass Secureye's rate limiting and abuse monitoring. You're responsible for preventing token replay and brute-force attacks on your signing endpoint.
